# Handoff to the Linux x86_64 host, 2026-11-11

From the Mac (Apple M5 Max, macOS 27.0.1). Pull `main` at `1598e69` or later.
M8C's E1 to E6 passed on the Mac with SmolVM and with Nanos on libkrun. The
Linux x86_64 Nanos leg of every E is unverified.

## What changed on main

- **E4 files (`b3d419a`).** SmolVM sessions get a host directory,
  `<BCTL_HOME>/files/<session>`, mounted at the guest's
  `/home/browser/Downloads`. On Nanos, `bctl inspect` reports no
  `files_dir`, and the interop suite expects that. The guest supervisor
  (`guest/appliance/src/supervise.rs`) now creates and chowns
  `~browser/Downloads` on every runtime. That is harmless on Nanos, and a
  `nanos-helium` rebuild picks it up but does not need to.
- **E5 (`a9ee602`).** `bctl agent-browser-plugin` is agent-browser's
  `browser.provider` (`docs/agent-browser.md`). `bctl cdp-revoke` takes
  `--url`.
- **E6 (`6500b15`).** `BCTL_INTEROP_SUITE=measure tests/interop/run.sh` times
  the clients, and `docs/compatibility.md` is the feature matrix.
- **Mac Nanos perf column rerun (`1598e69`)** with both CPUs online.

## Decide or build (Hydrogen and the Nanos runtime)

- **Nanos has no files directory.** Hydrogen needs to mount a host directory
  (9p or virtiofs). The bctl side would then need three changes:
  - a `files_dir` in `bctl_runtime_nanos::LaunchSpec`;
  - mounting it at `/home/browser/Downloads`;
  - widening `Daemon::files_dir` (`crates/bctl/src/daemon.rs`), which is
    SmolVM-only today.

  The guest already chowns the mount point.
- **The arm64 pin `bbeea356` lacks the x86 FIONREAD fix `df949087`.**
  `runtime/build-nanos-arm64.sh` and `runtime/build-nanos.sh` pin different
  Hydrogen revisions. Please give arm64 a revision that has both
  `bbeea356`'s AP start fix and `df949087`. `bbeea356` changes only how
  arm64 secondary CPUs start; x86 is unaffected.
- **Nanos `remove` can orphan a VM.** `crates/runtime-nanos/src/lib.rs:286`
  treats a control socket that is missing or refuses connections as a
  stopped machine, and deletes the machine directory anyway. One Mac
  interop run left a supervisor and its `nanos-krun` running at 200 percent
  CPU after bctl reported the session gone.
  - It did not recur in 5 manual reclaim loops or in 3 full suite runs.
  - E5's reclaim no longer reuses a machine name, which may have been the
    trigger.
  - A fix would have the supervisor record its PID and make `remove` stop
    that process before deleting anything. That change touches both
    supervisors.
- **One Mac Nanos interop run failed an owner-death relaunch.**
  agent-browser's 30 s read timeout fired (`EAGAIN`). In isolation the same
  relaunch took 1.1 s in 5 of 5 tries, so this may be the same guest stall.
  Watch for it on Linux.
